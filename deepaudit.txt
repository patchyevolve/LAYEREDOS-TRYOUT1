## 3. LAYER-BY-LAYER AUDIT

### 3.1 PMM — Physical Memory Manager (`pmm.c`)

**Total lines: 187** | **Modified in this session: Yes**

#### What was changed:
The free list was changed to store kernel virtual addresses (via `PHYS_TO_VIRT`) instead of raw physical addresses. This was required because:

- Syscall handlers (ISR 0x80) use `int 0x80` which runs with user-mode page tables (CR3 pointing to the user process's PML4)
- The user PML4 does NOT have identity mapping of the first 512 MB
- If `free_list` contained physical addresses, dereferencing `free_list` (to follow `page->next`) would triple-fault when a syscall handler allocated or freed memory
- By storing kernel virtual addresses (`PHYS_TO_VIRT(phys_addr)`), the free list is always accessible via the higher-half mapping

#### Key changes (pmm.c):

| Line(s) | Change |
|---------|--------|
| 16 | `used_bitmap` comment updated to note PHYS_TO_VIRT usage |
| 51 | `pmm_alloc_page`: `VIRT_TO_PHYS(page)` to get physical from virtual freelist node |
| 54 | `kmemset((void*)PHYS_TO_VIRT(phys), ...)` — clear page via kernel VA |
| 84 | `pmm_alloc_pages`: `VIRT_TO_PHYS(cur)` to compare freelist nodes |
| 95 | `kmemset((void*)PHYS_TO_VIRT(...), ...)` — clear allocated pages |
| 110 | `pmm_free_page`: `(free_page_t*)PHYS_TO_VIRT(phys_addr)` to add to freelist |
| 130 | `add_region_to_free_list`: `(free_page_t*)PHYS_TO_VIRT(phys)` to create freelist |

#### Analysis:
- `VIRT_TO_PHYS` macro converts a kernel virtual address (>= `KERNEL_VMA_BASE = 0xFFFFFFFFC0000000`) to physical by subtracting the base. Since all PMM pages are within the first 512 MB, and the higher-half mapping covers exactly the first 512 MB at `KERNEL_VMA_BASE` to `KERNEL_VMA_BASE + 512 MB`, this conversion is correct.
- `PHYS_TO_VIRT` is the inverse: `phys + KERNEL_VMA_BASE`.
- **Edge case:** If physical memory above 512 MB were allocatable, the higher-half mapping would not cover it, and `PHYS_TO_VIRT` would produce an unmapped address. The current boot page tables map only 512 MB (PD[0..255] as 2 MB pages). `pmm_init` reports total memory up to 512 MB. This is a physical memory ceiling, not a correctness boundary.

#### Remaining issues:
- `pmm_alloc_pages` scans the entire bitmap O(N) and the free list O(N×M) for multi-page allocations. For small counts (≤ 4 pages for boot files) this is acceptable.
- Double-free silently ignored (`if (!bitmap_test(idx)) return;`). Should panic per spec.

### 3.2 VFS — Virtual Filesystem Layer (`vfs.c` / `vfs.h`)

**Total lines: 273 + 64 header** | **Modified in this session: Yes (minor)**

#### Architecture:

The VFS is a thin abstraction layer that:
1. Maintains a `mounted_fs` pointer (only one filesystem at a time)
2. Provides `vfs_find` for path walking — uses `readdir` ops if available, falls back to children linked list
3. Provides `vfs_open`/`vfs_close`/`vfs_read`/`vfs_write`/`vfs_lseek` — fd-based I/O
4. Provides `vfs_create`/`vfs_mkdir`/`vfs_unlink` — creation and deletion

#### `vfs_find` path walking (vfs.c:46-123):

Two modes:
1. **Modern (readdir-based):** If `mounted_fs->ops->readdir` exists, walks the path by calling `readdir` on each directory node to find the next component. This is the SFS path.
2. **Legacy (children-list):** Falls back to the `children` linked list. This is the old ramdisk path.

**Bug in modern mode (vfs.c:70-85):**
```c
while (1) {
    vfs_node_t* child = NULL;
    if (cur->fs && cur->fs->ops && cur->fs->ops->readdir) {
        int r = cur->fs->ops->readdir(cur, idx, &child);
        if (r != 0 || !child) break;
    } else {
        break;
    }
    int match = 1;
    for (int i = 0; i < len; i++) {
        if (child->name[i] != start[i]) { match = 0; break; }
    }
    if (match && child->name[len] == '\0') {
        found = child;
        break;
    }
    idx++;
}
```

- **Memory leak:** For non-matching children returned by `readdir`, the `child` node (and its `private_data`) is never freed. Every path walk leaks `O(directory_size)` nodes. For a directory with 100 files, `vfs_find` leaks 99 child nodes per call. For a command like `cat /subdir/f.txt`, this leaks one node for each non-matching sibling. Not a crash-causing bug on 512 MB RAM, but unbounded.

#### `vfs_create` (vfs.c:203-235):

- Extracts parent directory path and filename from the full path
- Calls `vfs_find(parent_path)` to get the parent directory node
- Calls `mounted_fs->ops->create(parent, name, is_dir)`
- **Duplicate code:** `vfs_unlink` (vfs.c:241-273) is essentially identical logic

### 3.3 SFS — Simple Filesystem (`sfs.c` / `sfs.h`)

**Total lines: 540 + 55 header** | **Modified in this session: Yes (extensively)**

#### On-disk format:

```
Block 0:       Superblock (512 bytes)
Block 1..N:    Inode bitmap (N = ceil(1024 inodes / (512*8 bits)))
Block N+1..M:  Block bitmap (M = ceil(total_blocks / (512*8 bits)))
Block M+1..P:  Inode table (P = ceil(1024 inodes / (512/64 inodes_per_block)))
Block P+1..:   Data blocks
```

- **Block size:** 512 bytes (SFS_BLOCK_SIZE)
- **Max inodes:** 1024 (SFS_MAX_INODES)
- **Directory entries per block:** 512/32 = 16 (each dirent is 32 bytes: 4 byte inode + 28 byte name)
- **Max filename length:** 27 chars + null (SFS_NAME_MAX = 28)
- **Direct blocks per inode:** 12 (supports up to 12 × 512 = 6 KB inline)
- **Indirect block:** 1 per inode (supports up to 512/4 = 128 additional blocks = 64 KB via indirect)

#### Key functions:

**`sfs_inode_get_block` (sfs.c:114-153):**
- Returns the physical block number for a given file block number
- For `file_block < 12`: uses `inode->direct[file_block]` (direct blocks)
- For `file_block >= 12`: uses `inode->indirect` (single indirect block)
- With `create=1`: allocates new blocks on demand
- **Indirect block logic:**
  1. If `inode->indirect == 0` and create: allocate an indirect block, store in `inode->indirect`
  2. Read the indirect block (an array of `uint32_t` block pointers)
  3. At `ptrs[indirect_idx]`, if 0 and create: allocate a data block, store pointer, write back indirect block
  4. Return the data block number
- **Subtle issue:** When `create=0` (read path), if `inode->indirect == 0`, the function returns -1 immediately — correct, file has no indirect block
- **Subtle issue (sfs.c:137-138):** `kmemset(ibuf, 0, SFS_BLOCK_SIZE)` is called ON EVERY call when `create=1`, even if the indirect block already exists. This is harmless but wasteful — the subsequent `sfs_read_data` overwrites `ibuf` with the actual indirect block contents, making the `kmemset` pointless for existing blocks

**`sfs_vfs_readdir` (sfs.c:261-306):**

Critical function for directory listing. Key operations:
1. Refresh parent inode from disk: `sfs_read_inode(f->fs, f->inum, &f->inode)` — **THIS was the fix for the stale inode cache bug**
2. Compute `max_entries = f->inode.size / sizeof(sfs_dirent_t)`
3. If `index >= max_entries`, return -1 (end of directory)
4. Compute the file block and offset for the entry index
5. Read the data block
6. Extract the `sfs_dirent_t` at the offset
7. Allocate a `vfs_node_t` child with name from the dirent
8. Read the child's inode from disk for `child->size` and `child->flags`
9. Allocate `sfs_file_t` private_data for the child with fresh inode data

**Stale inode cache bug (FIXED):**

Root cause: When `vfs_find` walked a path like `/subdir/f.txt`, it called `readdir` on each directory. Each `readdir` call created a child node with `private_data` containing a cached copy of the child's inode (size, direct blocks, etc.). If a subsequent operation (like `vfs_create` or `vfs_write`) modified the child directory (e.g., adding a new file to a subdirectory), the cached inode in the child's `private_data` became stale. The next `readdir` call on that child would use the stale `f->inode.size` to compute `max_entries`, potentially returning fewer entries than actually exist on disk.

Fix: Added `sfs_read_inode(f->fs, f->inum, &f->inode)` at the start of `sfs_vfs_readdir` (sfs.c:265). This refreshes the directory's inode from disk before computing `max_entries` and reading dirents.

**`sfs_add_dirent` (sfs.c:341-367) — CRITICAL FIX:**

Original code:
```c
int64_t ret = sfs_vfs_write((vfs_node_t*)fs->vfs_fs.root, &de, sizeof(de), size);
```

This ALWAYS wrote the dirent to `fs->vfs_fs.root` — the root directory — regardless of which directory was the actual parent. Creating a file in `/subdir/f.txt` would add the dirent to root instead of to `subdir`'s data blocks.

Fixed code:
```c
vfs_node_t parent_node;
sfs_file_t parent_file;
// ... initialize parent_file with dir_inum
parent_node.fs = &fs->vfs_fs;
parent_node.private_data = &parent_file;
int64_t ret = sfs_vfs_write(&parent_node, &de, sizeof(de), size);
```

This creates a temporary `vfs_node_t` wrapping a `sfs_file_t` that points to the correct parent directory's inode. The write goes to the correct directory's data blocks.

**Consequence:** After this fix, `sfs_vfs_write` modifies `parent_file.inode` (stack-local), not the original caller's `f->inode`. This means the caller's `f->inode.size` is NOT updated. The `sfs_read_inode` at the start of `sfs_vfs_readdir` fixes this by reading the latest inode from disk on each call.

**`sfs_vfs_create` (sfs.c:393-419):**

- Validates dir node and private_data
- Checks if name already exists via `sfs_lookup`
- Allocates a new inode
- Writes initial inode (type=FILE or DIR, size=0)
- Calls `sfs_add_dirent` to link into parent
- On failure: frees the allocated inode
- **Leaves [SFS_CREATE] debug prints** for error cases (no private_data, not a dir, name exists) — only fire on failures

**`sfs_vfs_unlink` (sfs.c:421-451):**

- Looks up the child inode number by name
- Frees all data blocks: iterates `direct[0..11]` and the indirect block (frees each indirect pointer, then the indirect block itself)
- Removes the dirent from the parent directory (sets `de->inode = 0`)
- Frees the child inode
- **Note:** Does NOT update the parent directory's inode size after removing the dirent. The size remains unchanged (the dirent slot is zeroed but still counts toward `max_entries` on subsequent reads). `sfs_vfs_readdir` checks `if (de->inode == 0) return -1;` at sfs.c:281, so zeroed entries are skipped. This is correct and avoids the complexity of shrinking the directory.

**`sfs_format` (sfs.c:453-497):**

- Writes superblock at block 0
- Zeros metadata blocks (bitmaps + inode table)
- Marks inode 0 as used in the inode bitmap
- Creates root inode (inum=0, type=DIR, size=0)
- **Note:** Does NOT clear data blocks (blocks >= `data_start`). Only metadata is zeroed. Data blocks retain whatever content the ramdisk had (all zeros from `ramdisk_blk_init`'s `kmemset`).

**`sfs_mount` (sfs.c:499-538):**

- Allocates `sfs_fs_t` and reads superblock
- Validates magic number
- Sets up VFS node tree: `fs->vfs_fs.root = &fs->root_node`
- Creates `sfs_file_t` private_data (`rf`) with inum=0 (root)
- Reads root inode from disk into `rf->inode`
- Registers with VFS via `vfs_register_fs`
- **Note:** `fs->root_node.children` is NOT populated — SFS does not use the children linked list. Path walking goes through `readdir`.

#### Memory layout for a typical boot:

After format + mount + 4 boot files + mkdir:

```
SFS Block 0:    Superblock
Block 1:        Inode bitmap (bit 0 set = root used, bit 5 set = 5 inodes used)
Block 2:        Block bitmap (first ~7 data blocks used)
Block 3-18:     Inode table (16 blocks × 8 inodes/block = 128+ inodes)
Block 19:       Data block 0 — root dir entries (hello.elf, cat.elf, version.txt, welcome.txt, subdir)
Block 20:       Data block 1 — hello.elf content (~9680 bytes spans multiple blocks)
Block 21:       Data block 2 — hello.elf continuation (~9680/512 = 19 blocks)
...
Block 38+:      Data blocks for cat.elf, version.txt, welcome.txt files
Block N:        Data block for subdir dir entries
Block N+1:      Data block for subdir/f.txt content (3 bytes)
```

Each SFS block is 512 bytes. A 9680-byte ELF file spans 19 data blocks (9680/512 = 18.9). All 12 direct blocks and 7 indirect blocks are used.

### 3.4 Block Device Layer (`block.c` / `block.h`)

**Total lines: 38 + header** | **Modified in this session: No**

Simple registry of up to 8 block devices. Provides:
- `block_read` / `block_write` — dispatch to device-specific functions
- `block_register` — add a device
- `block_find` — look up by name

**No locking.** Called from SFS which may run in any thread context. If the scheduler preempts a thread during a block read/write, another thread could corrupt the block device state. Currently acceptable because only one thread (the shell) accesses the block device.

### 3.5 Ramdisk Block Device (`ramdisk_blk.c` / `ramdisk_blk.h`)

**Total lines: 47 + 8 header** | **Modified in this session: Yes (size change)**

#### Key parameters:
- `RAMDISK_BLK_SIZE`: 1 MB (was 4 MB, reduced to save physical pages)
- `BLOCK_SIZE`: 512 bytes (from block.h, typically)
- Total blocks: 2048

#### PMM allocation:
```c
uint64_t pages = (RAMDISK_BLK_SIZE + PAGE_SIZE - 1) / PAGE_SIZE;  // 256 pages
uint64_t phys = pmm_alloc_pages(pages);
```
Allocates 256 4 KB pages from PMM. Uses `PHYS_TO_VIRT(phys)` for the kernel-accessible pointer.

**No filesystem caching / write-back:** Every SFS `sfs_write_block` immediately calls `ramdisk_blk_write` which `kmemcpy`s to the ramdisk buffer. No delayed writes, no journaling.

### 3.6 Shell Commands (`shell.c`)

**Total lines: 649** | **Modified in this session: Yes**

#### `cmd_ls` (shell.c:333-368):

Two code paths:
1. **SFS path (readdir):** If the directory node has `ops->readdir`, iterates calling `readdir`, prints each child, frees the child node and its private_data
2. **Ramdisk fallback (children list):** If no readdir, iterates `dir->children` linked list

**Important:** Freed child nodes and private_data in the readdir path. The root node is NOT freed — it's persistent. This is critical because `mounted_fs->root` points to `fs->root_node` in SFS, and freeing it would corrupt the entire filesystem.

**Bug in cmd_ls:** Non-matching children from readdir are not freed by `vfs_find` (see VFS audit above). The `cmd_ls` function only frees the children it iterates (`idx++` loop). If `vfs_find` pre-loaded children (it doesn't — it walks paths on each call), those would leak. Currently safe because `cmd_ls` calls `vfs_find("/")` which returns the persistent root node, then iterates via readdir.

#### `cmd_cat` (shell.c:370-382):

- Opens file, reads in 255-byte chunks, prints each chunk
- Appends a newline at the end
- Closes the file (frees the node and private_data)
- **No bounds checking on file size:** If a file is > 256 bytes, the loop reads multiple chunks. But `buf` is 256 bytes, and `vfs_read` returns up to 255 bytes at a time (sizeof(buf)-1). This is correct.

#### `cmd_writefile` (shell.c:493-505):

- Attempts to open file for writing (flag=1)
- If open fails (file doesn't exist), calls `vfs_create`, then re-opens
- Writes the text argument using `kstrlen` for size
- Closes the file
- Prints "writefile: ok" on success

#### `cmd_mkdir` (shell.c:481-485):

- Calls `vfs_mkdir` which calls `vfs_create(path, 1)`
- Prints error on failure

#### `cmd_rm` (shell.c:487-491):

- Calls `vfs_unlink`
- Prints error on failure

#### Shell command table (shell.c:545-570):

```
help, ls, cat, writefile, mkdir, rm, format, run, ps, top,
mutex, usermode, loop, fault, kbtest, atatest, hlt, clear, reboot
```

**Missing:** `rmdir` command is NOT registered despite `sfs_vfs_unlink` being able to remove directories.

### 3.7 Main / Boot Sequence (`main.c`)

**Total lines: 191** | **Modified in this session: Yes**

#### Boot file copy logic (main.c:92-130):

```c
vfs_create("/hello.elf", 0);
int fd = vfs_open("/hello.elf", 1);
if (fd >= 0) {
    vfs_write(fd, _binary_build_user_program_elf_start, hello_sz);
    vfs_close(fd);
}
```

Four boot files are created in SFS:
1. `/hello.elf` — user-mode ELF program (~9.5 KB)
2. `/cat.elf` — user-mode cat program (~10 KB)
3. `/version.txt` — "OPERtur/TRY1 OS v0.2.0\nLayered x86-64 Kernel\n" (48 bytes)
4. `/welcome.txt` — "Welcome to OPERtur!\n" (20 bytes)

**Note:** `readme.txt` (added to old ramdisk at line 72) is NOT copied to SFS. This is a minor inconsistency — the old ramdisk has 5 files, SFS has 4.

#### Boot-time test (main.c:148-156):

After boot complete, lists SFS root via `root->children` (not readdir). This works because `vfs_register_fs` sets `root_node.children = fs->root` (main.c:29 in vfs.c). The SFS root node (`fs->root_node`) is used as both VFS root and SFS root. `fs->root_node.children` is never populated by SFS, so this test lists `children` which is NULL. Wait — let me check:

In `vfs_register_fs` (vfs.c:23-32):
```c
root_node.fs = fs;
if (fs->root) {
    fs->root->parent = &root_node;
    root_node.children = fs->root;
}
```

So `root_node.children = fs->root` = `&fs->root_node`. `fs->root_node.children` is NULL (never set by SFS). The boot test iterates `root->children` which is `fs->root_node`. But `fs->root_node.children` is NULL. So the loop:
```c
vfs_node_t* child = root->children;
while (child) { ... child = child->next; }
```

The first iteration: `child = &fs->root_node` (non-NULL). Prints "FILE: /" (or whatever `fs->root_node.name` is — which is "/"). Then `child = fs->root_node.next` which is NULL. Loop ends. So the boot test prints only "FILE: /" — not the actual files. This is a cosmetic bug in the boot-time test, but it doesn't affect functionality.

## 4. CRITICAL BUGS FOUND & FIXED

### BUG-F1 — `sfs_add_dirent` always writes to root directory (CRITICAL)
**File:** `sfs.c:341-367`  
**Status: FIXED**

**Bug:** `sfs_add_dirent` called `sfs_vfs_write((vfs_node_t*)fs->vfs_fs.root, ...)` regardless of `dir_inum`. Creating a file in `/subdir/f.txt` added the dirent to root's data blocks, not the subdirectory's. Subsequent reads of `/subdir` found no files, writes created orphaned on-disk entries in root.

**Impact:** Subdirectory operations completely broken. Files appeared in root when they should be in subdirs.

**Fix:** Create a temporary `vfs_node_t` with `private_data` pointing to a stack-local `sfs_file_t` initialized with the correct `dir_inum` and fresh inode from disk.

### BUG-F2 — Stale inode cache in readdir (CRITICAL)
**File:** `sfs.c:261-306`  
**Status: FIXED**

**Bug:** `sfs_vfs_readdir` used `f->inode.size` (cached in `private_data` at node creation time) to compute `max_entries`. After a directory was modified (e.g., a file added to a subdirectory), the cached inode size was stale. `vfs_find` walking a path like `/subdir/f.txt` would:
1. Find "subdir" in root via readdir → creates subdir node with fresh inode (size=0, just created by mkdir)
2. Try to find "f.txt" in subdir via readdir → uses cached inode from step 1 (size=0, max_entries=0)
3. Returns -1 immediately → `vfs_find` returns NULL → "File not found"

**Impact:** All path walking into modified directories failed. `cat /subdir/f.txt`, `ls /subdir`, and any operation requiring path resolution after a directory was modified would fail.

**Fix:** Added `sfs_read_inode(f->fs, f->inum, &f->inode)` at the start of `sfs_vfs_readdir` (sfs.c:265) to refresh the inode from disk on every readdir call.

### BUG-F3 — PMM free list uses raw physical addresses (HIGH)
**File:** `pmm.c:43-55, 100-114, 122-137`  
**Status: FIXED**

**Bug:** The PMM free list stored physical addresses as `free_page_t*` pointers. Dereferencing these pointers to read `page->next` required the physical address to be valid as a virtual address. This worked only because the boot page tables identity-mapped the first 512 MB. When a syscall handler ran with user CR3 (which lacks identity mapping), dereferencing the free list caused a page fault.

**Impact:** Any memory allocation or deallocation during a syscall (e.g., `writefile` calling `vfs_write` which may allocate SFS blocks via `sfs_alloc_block` → `pmm_alloc_page`) would crash with a triple fault if the free list page was above the user-mapped region.

**Fix:** Changed all free list operations to use `PHYS_TO_VIRT` when storing/reading free list pointers, and `VIRT_TO_PHYS` when computing the physical page number for bitmap operations.

### BUG-F4 — `cmd_ls` frees the persistent root node (CRITICAL)
**File:** `shell.c:333-368` (original code)  
**Status: FIXED**

**Bug:** The original `cmd_ls` freed `dir->private_data` (which is `rf` — the root node's private_data) and freed `dir` (which is `mounted_fs->root` — the persistent root node). After the first `ls` command, the SFS root node was deallocated. All subsequent `vfs_find` operations would dereference freed memory in `mounted_fs->root->private_data`.

**Impact:** Any file operation after the first `ls` would crash or produce garbage. Files appeared and disappeared unpredictably.

**Fix:** Changed `cmd_ls` to NOT free the root node or its private_data. The root node is persistent for the lifetime of the filesystem.

### BUG-F5 — Ramdisk block size too large (LOW)
**File:** `ramdisk_blk.c:5`  
**Status: FIXED**

**Bug:** `RAMDISK_BLK_SIZE` was 4 MB (1024 pages at 4 KB each). For a system with 512 MB RAM, this consumed 0.8% of total memory. Excessive for a teaching kernel.

**Fix:** Changed to 1 MB (256 pages). Still enough for SFS superblock, bitmaps, inode table, and ~100 KB of data.

## 5. REMAINING CRITICAL BUGS

### BUG-R1 — `vfs_find` leaks child nodes on non-matching readdir
**File:** `vfs.c:68-85`  
**Severity:** Medium  
**Status:** Unfixed

Each non-matching child returned by `readdir` is never freed. A directory with 100 files causes 99 leaked `vfs_node_t` + `sfs_file_t` allocations per path walk. Over time (e.g., in a shell loop), this exhausts kernel heap memory. Fix: Free non-matching children before continuing the loop.

### BUG-R2 — No `rmdir` shell command
**File:** `shell.c`  
**Severity:** Low  
**Status:** Unfixed

While `vfs_unlink` works for directories (tested via `rmdir` call, though no shell command exists), there is no `cmd_rmdir` in the command table. The `rm` command uses `vfs_unlink` which works for both files and directories.

### BUG-R3 — Boot-time test lists only root node, not files
**File:** `main.c:149-156`  
**Severity:** Cosmetic  
**Status:** Unfixed

The boot test iterates `root->children` which is `fs->root_node` (not actual files). Fix: Use `readdir` or iterate `fs->root_node.children` (but SFS doesn't populate children list).

### BUG-R4 — `readme.txt` not copied to SFS
**File:** `main.c:70-128`  
**Severity:** Low  
**Status:** Unfixed

`readme.txt` is added to the old ramdisk but not copied to SFS. Inconsistency — boot files should be consistent.

### BUG-R5 — No write size validation in `cmd_writefile`
**File:** `shell.c:502`  
**Severity:** Low  
**Status:** Unfixed

`vfs_write(fd, args[2], kstrlen(args[2]))` writes the raw argument string. If the text contains null bytes (it can't via the shell parser, but in theory), the write would be truncated. Currently irrelevant since the shell parser stops at null bytes.

## 6. DESIGN QUALITY OBSERVATIONS

### Good design decisions:

1. **SFS block size = 512 bytes.** Matches standard block device sector size. Simple and compatible.

2. **Indirect block supports up to 64 KB files.** With 12 direct blocks (6 KB) + 128 indirect pointers (64 KB), the maximum file size is 70 KB. For the current use case (small boot files, text files, small ELFs), this is sufficient.

3. **Inode cache refresh in readdir.** The fix forces a disk read on every readdir call. This eliminates stale cache issues at the cost of one block read per directory per walk. Since directories are small, this is acceptable.

4. **Temporary `vfs_node_t` for `sfs_add_dirent`.** Instead of modifying `sfs_vfs_write` to accept a raw `sfs_file_t*` (which would break the VFS abstraction), creates a minimal VFS-compatible wrapper. Clean abstraction boundary.

5. **Zeroed entries in directory data.** `sfs_remove_dirent` sets `de->inode = 0` rather than shifting remaining entries. `sfs_vfs_readdir` checks for zeroed entries and skips them. Simple, correct, avoids fragmentation.

6. **PMM virtual-address free list.** Using `PHYS_TO_VIRT`/`VIRT_TO_PHYS` throughout the PMM free list ensures correctness regardless of which page tables are active. This is the architecturally correct approach per the spec.

7. **`pmm_alloc_page` clears the page outside the critical section.** The `kmemset` at pmm.c:54 is AFTER `hal_restore_irq`. While this means the page is briefly "allocated but not cleared," no other thread can see it because the bitmap is already set and the page is removed from the free list. Correct and minimizes IRQ-disable time.

### Design concerns:

1. **No filesystem journaling / WAL.** All writes are synchronous and in-place. A crash during `sfs_add_dirent` can leave the directory in an inconsistent state (dirent written to data block but inode size not updated).

2. **`sfs_vfs_readdir` allocates from heap per call.** Each `readdir` call `kmalloc`s a `vfs_node_t` and an `sfs_file_t`. `vfs_find` leaks non-matching children. Even matching children must be explicitly freed by the caller. This allocation-heavy pattern is fine for light shell use but would be problematic for a server workload.

3. **No file locking or concurrent access protection.** If the scheduler ran multiple threads accessing SFS simultaneously, data corruption would occur. Currently the shell runs as the only thread accessing the filesystem.

4. **`sfs_remove_dirent` does not shrink the directory inode size.** After removing all entries from a directory, the inode still shows `size=32*N` for the maximum index ever used. `sfs_vfs_readdir` scans all entries linearly, reading blocks even for directories that are almost empty. Wasteful but not incorrect.

5. **`sfs_lookup` reads each directory block multiple times.** For a directory with 32 entries (2 blocks), `sfs_lookup` may read both blocks. `sfs_lookup` is called from `sfs_vfs_create` (before adding) and `sfs_vfs_unlink` (before removing). Each call re-reads the directory from disk. Caching the directory blocks would improve performance for multi-step operations.

6. **`pmm_alloc_pages` O(N²) free list scan.** For each page in a multi-page allocation, the entire free list is scanned to find and remove the page. For 256 pages (1 MB ramdisk), this is 256 × 131k = ~33 million pointer traversals. Acceptable for boot-time (once), but would be problematic for dynamic allocation.

7. **Stack allocation of 512-byte buffers.** Functions like `sfs_inode_get_block` allocate `uint8_t ibuf[SFS_BLOCK_SIZE]` (512 bytes) on the stack. The kernel stack is 16 KB (4 pages), so this is acceptable. But multiple nested calls could stack-overflow. Stack depth analysis:
   - `sfs_vfs_write` (shell call) → calls `sfs_inode_get_block` (512 B temp) → calls `sfs_writelink` (512 B temp)
   - Worst case: ~1.5 KB of stack for the deepest SFS call chain
   - Available stack: 16 KB — safe margin (~10x)

8. **`sfs_vfs_read` and `sfs_vfs_write` lack `f->inode.type` verification on every call.** `sfs_vfs_write` checks `if (f->inode.type != SFS_TYPE_FILE)` but `sfs_vfs_read` does not. Reading from a directory node (type=SFS_TYPE_DIR) would return garbage from its data blocks rather than failing with an error. This works because directories never have their blocks read via `vfs_read` (only via `readdir`), but it's a latent correctness issue.

## 8. WHAT DOES NOT WORK / MISSING

### Functional gaps:

| Feature | Status | Notes |
|---------|--------|-------|
| `rmdir` shell command | Missing | `vfs_unlink` works for dirs but no `cmd_rmdir` |
| Large file support (> 64 KB) | Missing | Indirect block limit: 70 KB max file size |
| File append (O_APPEND) | Missing | `vfs_open` flags=1 for write, always from offset 0 |
| File truncation | Missing | No `ftruncate` or O_TRUNC; overwriting requires rm+create |
| Multiple filesystem support | Missing | Only one `mounted_fs` slot |
| Block device caching | Missing | Every block read/write goes to ramdisk directly |
| Directory atime/mtime/ctime | Missing | Inode has no timestamp fields |
| Hard links | Missing | One inode per name |
| Symbolic links | Missing | No symlink inode type |
| Permissions / ownership | Missing | `mode` field in inode is stored but never set or checked |
| File descriptor stdio | Partial | fd 0/1/2 reserved but not connected to UART |
| Concurrent access | Missing | No locking in VFS, SFS, or block layer |
| Reading ELF files from SFS | Unknown | `cmd_run` uses `vfs_open`/`vfs_read` — should work but not tested |

### Known limitations:

1. **SFS block count limited by ramdisk size.** 1 MB ramdisk = 2048 blocks. Metadata consumes ~20 blocks (superblock + bitmaps + inode table). Data blocks: ~2028. Each block is 512 bytes. Maximum total file data: ~1 MB minus metadata. Enough for boot files + small user files.

2. **Maximum files:** 1024 inodes total (SFS_MAX_INODES). One reserved for root. 1023 files maximum.

3. **Maximum directory entries per block:** 16 (512/32). A directory with 32+ entries spans 2+ blocks. Multiple levels of indirect pointers would be needed for directories larger than 12 × 16 = 192 entries + indirect 128 × 16 = 2048 entries. Theoretical max: 2240 entries per directory.

4. **File write always truncates to offset.** `sfs_vfs_write` overwrites data at `offset` but does not truncate beyond the new end. If a file has 100 bytes and you `write(fd, "x", 1)` at offset 0, the file becomes 100 bytes with the first byte overwritten. The old data beyond the new write remains. This is correct POSIX semantics for write without O_TRUNC.

5. **No consistency guarantees on crash.** SFS writes superblock, bitmaps, inode table, and data blocks independently. A crash between any of these writes can leave the filesystem in an inconsistent state requiring `sfs_format` to repair.
